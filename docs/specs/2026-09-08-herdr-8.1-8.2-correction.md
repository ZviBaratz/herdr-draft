# Correction to 2026-09-03 placement spec, §2.4 and §8.1

Status: correction note. Supersedes the cited claims in
`2026-09-03-placement-and-pane-ownership-design.md`; the rest of that document
stands. Written after verifying §8 against herdr at HEAD `b1ff4582` and
reproducing both claims live.

## §2.4 and §8.1 rest on a misreading of herdr's close guard

The spec claims `close_pane` "refuses exactly this", and that the guard is merely
absent from `handle_pane_move`. It does not refuse.

The guard runs `confirm_implicit_worktree_group_close` →
`workspace_close_would_close_worktree_group` → `workspace_close_indices`, and
`workspace_close_indices` filters on `!space.is_linked_worktree`
(`src/app/actions.rs:1974`). It therefore fires only when the target is the
*primary repo workspace* of a group with two or more members — only when the
close would cascade into sibling workspaces. It never fires for a linked worktree
workspace.

Verified live on herdr 0.8.2, whose `src/app/api/panes.rs` is byte-identical at
HEAD: `herdr pane close <last pane of the linked worktree workspace>` returns
`{"type":"ok"}` and closes it with no confirmation.

So for the workspace herdr-draft actually cares about there is no protection to be
symmetric with, and `pane move` is not an outlier. §2.4's closing observation —
that the guard is conditional and a design must not rely on it — was right, and is
in fact stronger than it claimed.

## Consequences

**§8.1 cannot be cited as a herdr bug that might be fixed upstream.** The
surviving claim is narrower — primary repo workspaces only — and is already open
as herdrdev/herdr#1750, "Close confirmation is inconsistent across close paths",
untouched since 2026-07-22. `pane move` has now been added to that thread. Anything
that assumes membership will one day survive a `pane move` should assume the
opposite.

**§8.2 is herdr's stated contract, not an oversight.** `worktree open` performs
the identical stamping on its own reuse branch
(`src/app/api/worktrees.rs:139-145`); a test pins it on a workspace matched only by
a subdirectory cwd (`worktrees.rs:1462-1467`); the socket API docs describe it
("an existing workspace gains or changes worktree provenance",
`socket-api.mdx:411`); and a maintainer stated it closing herdrdev/herdr#3620 on
2026-09-04: "Worktree grouping is explicit provenance attached by `worktree create`
or `worktree open`."

§5.2's fail-closed policy remains the right call, but it should be justified as
working within herdr's contract rather than as routing around a bug awaiting a fix.

## Also worth recording

§8.2 does reproduce, including its consequence: a pre-existing two-tab user
workspace was reused by `worktree create --path <its cwd>`, stamped
`is_linked_worktree: true`, and then closed outright — unrelated tab included — by
`worktree remove --workspace`. The mechanism is real. It is simply intended.

CONTRIBUTING.
